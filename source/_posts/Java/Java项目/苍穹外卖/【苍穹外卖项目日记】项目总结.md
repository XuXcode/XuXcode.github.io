# 【苍穹外卖|项目日记】项目总结

## 项目收获

### 1、了解后端项目的整体结构和开发流程

通过这个项目，我进一步了解了后端项目的整体结构和分层架构。

项目主要按照 Spring MVC 常见的分层思想进行开发，基本开发流程为：

```text
Controller → Service → Mapper → 数据库
```

各层职责也逐渐明确：

- **Controller 层**：接收前端请求、处理请求参数，并调用 Service 层完成业务处理。
- **Service 层**：负责具体的业务逻辑，是整个业务处理的核心。
- **Mapper 层**：负责与数据库交互，完成增、删、改、查等操作。

通过实际开发，也逐渐养成了按照：

```text
Controller → Service → Mapper
```

这个顺序分析和实现业务功能的习惯。

同时，也理解了 `pojo` 包下不同对象的区别和作用：

- **Entity**：通常与数据库表结构相对应，用于数据库数据的存储和查询。
- **DTO（Data Transfer Object）**：主要用于接收前端传递过来的数据。
- **VO（View Object）**：主要用于封装后端返回给前端展示的数据。

简单理解：

```text
前端 → DTO → Controller → Service → Mapper → Entity
                                              ↓
前端 ← VO  ← Controller ← Service ← 查询结果
```

### 2、学会根据接口文档设计请求参数和返回值

通过这个项目，我逐渐学会了根据接口文档来编写 Controller 接口。

首先需要观察接口文档中的**请求方式、请求路径和请求参数**，判断前端传递的数据类型。

例如：

- 如果前端传递的是一组 JSON 数据，通常使用 DTO 对象接收；
- 如果只传递一个 `id`，则可以直接使用 `Long id` 等简单类型接收；
- 如果传递的是多个 id，可能使用 `List<Long>` 接收；
- 如果参数位于 URL 路径中，则通常使用 `@PathVariable`；
- 如果参数位于请求参数中，则通常使用 `@RequestParam`；
- 如果参数以 JSON 格式放在请求体中，则通常使用 `@RequestBody`。

除了请求参数之外，还需要根据接口文档要求判断后端应该返回什么数据。

`Result<T>` 中的泛型 `T` 表示返回给前端的 `data` 数据类型，例如：

```java
Result<String>          // 返回 String，例如 token

Result<User>            // 返回 User 实体对象

Result<OrderVO>         // 返回专门为前端展示封装的 OrderVO

Result<List<DishVO>>    // 返回 DishVO 集合

Result<PageResult>      // 返回分页查询结果
```

如果接口只是执行新增、删除、修改等操作，不需要返回具体业务数据，则可以直接：

```java
Result
```

或者更加规范地写成：

```java
Result<Void>
```

因此，在编写接口时可以按照下面的思路进行判断：

```text
看接口文档
    ↓
确定请求方式和路径
    ↓
判断前端传入什么数据
    ↓
选择 DTO / id / List 等参数类型
    ↓
Controller 接收请求
    ↓
Service 处理业务
    ↓
Mapper 操作数据库
    ↓
判断前端需要什么数据
    ↓
使用 Result<T> 返回对应的数据
```

通过这种方式，可以逐渐做到**根据接口文档独立分析并完成一个后端接口的开发**。

### 3、学会了使用 HttpClient 发送请求，调用第三方 API 接口

在苍穹外卖项目中，我接触并学习了如何使用 `HttpClient` 向第三方服务器发送 HTTP 请求，从而调用第三方提供的 API 接口。

我逐渐理解到，`HttpClient` 本质上就是一个 **Java 中用于发送 HTTP 请求的工具**。它可以模拟前端、浏览器或者其他客户端，主动向远程服务器发送 `GET`、`POST` 等请求，并获取对方返回的数据。

整体流程可以理解为：

```text
后端 Java 程序
    ↓
使用 HttpClient 构造 HTTP 请求
    ↓
向第三方服务器发送请求
    ↓
第三方服务器处理请求
    ↓
返回 JSON 等格式的数据
    ↓
Java 程序解析返回结果
    ↓
继续执行自己的业务逻辑
```

在苍穹外卖项目中，一个典型的应用场景就是 **微信小程序登录**。

前端登录后会向后端传递一个临时的 `code`，后端需要携带：

```text
appid
secret
code
grant_type
```

调用微信提供的登录接口。

流程大致为：

```text
微信小程序前端
    ↓
获取临时 code
    ↓
将 code 发送给苍穹外卖后端
    ↓
后端使用 HttpClient 调用微信 API
    ↓
微信服务器返回 openid 等数据
    ↓
后端解析 JSON
    ↓
根据 openid 查询或创建用户
    ↓
生成 JWT token
    ↓
返回给前端
```

其中，`openid` 可以理解为微信用户在当前小程序中的唯一身份标识，后端可以通过它识别当前登录的是哪一个用户。

在这个过程中，我理解了调用第三方 API 的基本思路：

#### 1. 准备请求地址和请求参数

首先根据第三方提供的接口文档，确定：

- 请求地址
- 请求方式，例如 `GET`、`POST`
- 请求参数
- 请求头
- 请求体格式
- 返回值格式

例如：

```java
Map<String, String> map = new HashMap<>();

map.put("appid", appid);
map.put("secret", secret);
map.put("js_code", code);
map.put("grant_type", "authorization_code");
```

这些参数并不是我们随便定义的，而是第三方 API 文档要求我们传递的。

------

#### 2. 使用 HttpClient 发送请求

准备好参数之后，就可以通过 HttpClient 将请求发送到指定的服务器。

例如：

```java
String json = HttpClientUtil.doGet(url, map);
```

这里可以简单理解为：

```text
url
+
请求参数 map
    ↓
HttpClient
    ↓
发送 GET 请求
    ↓
远程服务器
```

------

#### 3. 获取第三方服务器返回的数据

第三方服务器通常会返回 JSON 数据，例如：

```json
{
  "openid": "xxxxxx",
  "session_key": "xxxxxx"
}
```

此时 Java 程序拿到的通常还是一个 JSON 字符串：

```java
String json = HttpClientUtil.doGet(url, map);
```

所以还需要将 JSON 字符串解析成 Java 能够方便使用的数据。

例如：

```java
JSONObject jsonObject = JSON.parseObject(json);

String openid = jsonObject.getString("openid");
```

这样就可以从第三方服务器返回的数据中提取出我们真正需要的信息。

---

#### 对 HttpClient 的理解

现在我可以把 HttpClient 简单理解为：

> **HttpClient 是 Java 后端主动向其他服务器发送 HTTP 请求、调用第三方 API 的工具。**

以前我的理解主要是：

```text
前端 → 后端
```

学习 HttpClient 之后，我发现后端本身也可以作为一个“客户端”，主动请求其他服务器：

```text
前端
 ↓
自己的后端
 ↓
第三方服务器
```

例如：

```text
小程序
 ↓
苍穹外卖后端
 ↓
微信服务器
```

因此，一个后端项目并不一定只负责“接收请求”，它也可以主动发送请求，与其他系统进行通信。

---

#### 通过这一部分，我主要掌握了

1. 理解了 HttpClient 是 Java 中发送 HTTP 请求的工具；
2. 知道了后端也可以主动调用其他服务器提供的 API；
3. 学会根据第三方接口文档确定请求地址、请求方式和请求参数；
4. 了解了 `GET`、`POST` 请求的基本发送过程；
5. 学会获取第三方 API 返回的 JSON 数据；
6. 学会使用 JSON 工具将返回结果解析成 Java 可以使用的数据；
7. 理解了苍穹外卖中微信登录的基本流程；
8. 理解了 `code → 调用微信接口 → openid → 用户登录` 这一完整业务流程。

可以把整个知识点概括为：

```text
看第三方接口文档
    ↓
确定 URL、请求方式、请求参数
    ↓
使用 HttpClient 构造并发送请求
    ↓
获取第三方服务器响应
    ↓
解析 JSON 数据
    ↓
提取需要的字段
    ↓
继续执行自己的业务逻辑
```

这也是以后接入短信服务、地图服务、支付接口、AI 接口等第三方服务时都会反复使用到的一种开发思路。

### 4、学会了使用自定义注解、ThreadLocal 和 AOP 实现公共字段自动填充

在苍穹外卖项目中，很多数据库表都存在一些重复的公共字段，例如：

```java
createTime      // 创建时间
updateTime      // 修改时间
createUser      // 创建人
updateUser      // 修改人
```

例如新增菜品、新增套餐、修改员工信息时，都需要对这些字段进行赋值。

如果在每一个 Service 方法中都手动编写：

```java
entity.setCreateTime(LocalDateTime.now());
entity.setUpdateTime(LocalDateTime.now());
entity.setCreateUser(userId);
entity.setUpdateUser(userId);
```

会产生大量重复代码，而且容易出现漏写的问题。

因此，苍穹外卖项目通过：

```text
自定义 @AutoFill 注解
        +
       AOP
        +
   ThreadLocal
```

实现了公共字段的自动填充。

------

#### 1. 使用 ThreadLocal 保存当前登录用户 id

用户登录成功之后，前端后续发送请求时会携带 JWT Token。

后端拦截器解析 JWT Token 后，可以获取当前登录用户的 `id`：

```text
前端请求
   ↓
携带 JWT Token
   ↓
拦截器解析 Token
   ↓
获取当前用户 id
```

但是后面的 Service、AOP 等代码仍然需要知道：

> 当前这个请求到底是哪一个用户发起的？

因此项目中使用 `ThreadLocal` 保存当前用户的 id。

例如：

```java
public class BaseContext {

    public static ThreadLocal<Long> threadLocal = new ThreadLocal<>();

    public static void setCurrentId(Long id) {
        threadLocal.set(id);
    }

    public static Long getCurrentId() {
        return threadLocal.get();
    }

    public static void removeCurrentId() {
        threadLocal.remove();
    }
}
```

在拦截器解析出用户 id 后：

```java
BaseContext.setCurrentId(empId);
```

后续代码中就可以直接：

```java
Long userId = BaseContext.getCurrentId();
```

获取当前登录用户。

------

#### ThreadLocal 的理解

`ThreadLocal` 可以简单理解为：

> **给当前线程提供一个独立的变量存储空间。**

Web 项目中，每一个请求通常由一个线程进行处理，因此可以将：

```text
当前登录用户 id
```

与当前处理请求的线程绑定。

例如：

```text
用户A请求 → 线程1 → ThreadLocal中保存 id = 1

用户B请求 → 线程2 → ThreadLocal中保存 id = 2
```

两个线程中的数据互不影响。

所以，在当前请求处理过程中，只需要：

```java
BaseContext.getCurrentId();
```

就能够获取当前登录用户的 id，而不需要在：

```text
Controller
   ↓
Service
   ↓
Mapper
```

之间不断手动传递 `userId` 参数。

------

#### 2. 自定义 @AutoFill 注解

项目中定义了一个：

```java
@AutoFill
```

自定义注解。

它主要用于标记：

> 哪些 Mapper 方法需要进行公共字段自动填充。

例如：

```java
@AutoFill(value = OperationType.INSERT)
void insert(Employee employee);
```

或者：

```java
@AutoFill(value = OperationType.UPDATE)
void update(Employee employee);
```

这里通过：

```java
OperationType.INSERT
```

和：

```java
OperationType.UPDATE
```

区分当前执行的是：

```text
新增操作
```

还是：

```text
修改操作
```

因为两种操作需要填充的字段不同。

------

#### 3. 使用 AOP 拦截带有 @AutoFill 的方法

定义好 `@AutoFill` 注解之后，通过 AOP 创建切面，对带有该注解的 Mapper 方法进行统一处理。

整体思路：

```text
Mapper方法执行
     ↓
发现方法上存在 @AutoFill
     ↓
AOP进行拦截
     ↓
获取操作类型 INSERT / UPDATE
     ↓
获取当前时间
     ↓
通过 ThreadLocal 获取当前用户id
     ↓
自动给实体对象公共字段赋值
     ↓
继续执行 Mapper SQL
```

例如新增操作：

```java
@AutoFill(OperationType.INSERT)
void insert(Dish dish);
```

AOP 检测到：

```java
OperationType.INSERT
```

之后，就会自动填充：

```java
createTime
updateTime
createUser
updateUser
```

等字段。

相当于自动完成：

```java
dish.setCreateTime(LocalDateTime.now());
dish.setUpdateTime(LocalDateTime.now());
dish.setCreateUser(userId);
dish.setUpdateUser(userId);
```

因此 Service 中就不需要反复编写这些代码。

------

#### 4. 修改操作只需要填充部分字段

如果是：

```java
@AutoFill(OperationType.UPDATE)
void update(Dish dish);
```

那么通常只需要填充：

```java
updateTime
updateUser
```

即：

```java
dish.setUpdateTime(LocalDateTime.now());
dish.setUpdateUser(userId);
```

而：

```java
createTime
createUser
```

是在创建数据时确定的，不应该因为修改操作而发生改变。

因此可以理解为：

```text
INSERT
  ↓
createTime
createUser
updateTime
updateUser
```

而：

```text
UPDATE
  ↓
updateTime
updateUser
```

------

#### 整个公共字段自动填充流程

整个过程可以串起来理解为：

```text
用户登录
   ↓
获得 JWT Token
   ↓
前端携带 Token 发送请求
   ↓
拦截器解析 JWT
   ↓
得到当前用户 id
   ↓
BaseContext.setCurrentId(id)
   ↓
将用户 id 保存到 ThreadLocal
   ↓
Service 调用 Mapper
   ↓
Mapper 方法上存在 @AutoFill
   ↓
AOP 拦截 Mapper 方法
   ↓
判断 INSERT / UPDATE
   ↓
BaseContext.getCurrentId()
   ↓
获取当前操作用户 id
   ↓
自动填充时间和操作人字段
   ↓
执行 SQL
```

------

#### 这个功能涉及的几个知识点

通过公共字段自动填充功能，我进一步理解了以下几个知识点：

1. **自定义注解**

可以通过自己定义注解，例如：

```java
@AutoFill
```

给某些方法添加特殊的标记。

------

1. **AOP 面向切面编程**

AOP 可以在不修改原有业务代码的情况下，对一批符合条件的方法进行统一处理。

例如：

```text
日志记录
权限校验
事务
公共字段填充
```

都属于比较典型的 AOP 使用场景。

------

1. **ThreadLocal**

`ThreadLocal` 可以保存当前线程独有的数据。

在苍穹外卖中主要用于保存：

```text
当前登录用户 id
```

方便后续业务代码获取当前操作人。

------

1. **反射**

AOP 获取到实体对象后，可以通过反射调用：

```java
setCreateTime()
setUpdateTime()
setCreateUser()
setUpdateUser()
```

等方法，从而实现通用的字段赋值。

因此 AOP 不需要针对：

```text
Employee
Dish
Setmeal
Order
```

分别写一套代码，而是可以统一处理不同的实体对象。

------

#### 我的理解

这个功能本质上就是：

> **把多个业务中重复出现的“公共字段赋值”代码抽取出来，使用自定义注解标记需要自动填充的方法，再通过 AOP 统一完成处理。**

其中：

```text
@AutoFill
```

负责：

> **告诉 AOP 哪些方法需要处理。**

```text
ThreadLocal
```

负责：

> **保存并提供当前登录用户的 id。**

```text
AOP
```

负责：

> **真正执行公共字段自动赋值。**

可以最终概括为：

```text
JWT
 ↓
获取用户id
 ↓
ThreadLocal保存用户id
 ↓
@AutoFill标记Mapper方法
 ↓
AOP拦截
 ↓
获取当前时间 + 当前用户id
 ↓
自动填充公共字段
 ↓
执行SQL
```

通过这一部分，我不只是学会了公共字段自动填充，也第一次比较完整地理解了 **AOP、自定义注解和 ThreadLocal 在实际业务项目中是如何组合使用的**。

### 5、学会了使用 MyBatis 动态 SQL 处理不同查询条件

在苍穹外卖项目中，我学习了使用 MyBatis 的动态 SQL，根据前端传递的不同参数动态拼接 SQL 语句。

在实际开发中，查询条件往往不是固定的。例如分页查询员工、菜品、套餐或订单时，前端可能传递：

```text
name
status
categoryId
beginTime
endTime
```

但这些参数并不一定每次都有值。

如果直接写固定 SQL：

```sql
select *
from dish
where name = #{name}
  and status = #{status}
```

当 `name` 或 `status` 没有传递时，就可能导致查询条件不符合实际需求。

因此可以使用 MyBatis 动态 SQL：

```xml
<select id="pageQuery" resultType="Dish">
    select * from dish
    <where>
        <if test="name != null and name != ''">
            and name like concat('%', #{name}, '%')
        </if>

        <if test="status != null">
            and status = #{status}
        </if>

        <if test="categoryId != null">
            and category_id = #{categoryId}
        </if>
    </where>
</select>
```

这样只有当前端真正传递某个参数时，才会把对应的查询条件拼接到 SQL 中。

------

#### 1. `<if>`：判断某个条件是否需要拼接

`<if>` 是动态 SQL 中最常用的标签。

例如：

```xml
<if test="status != null">
    and status = #{status}
</if>
```

含义就是：

```text
如果 status 有值
    ↓
拼接 and status = ?
    
如果 status 没有值
    ↓
不拼接这一段 SQL
```

因此，动态 SQL 很适合处理：

> **查询参数可能有，也可能没有的情况。**

例如前端可能只按照姓名查询：

```text
name = 张三
status = null
```

最终 SQL 就可能变成：

```sql
select *
from employee
where name like '%张三%'
```

而不是强制再加一个 `status` 条件。

------

#### 2. `<where>`：自动处理 WHERE 和 AND

在动态 SQL 中，经常会将多个 `<if>` 放在 `<where>` 中：

```xml
<where>
    <if test="name != null">
        and name like concat('%', #{name}, '%')
    </if>

    <if test="status != null">
        and status = #{status}
    </if>
</where>
```

`<where>` 的作用可以理解为：

> **只有内部存在有效查询条件时才自动添加 `WHERE`，并且可以自动处理开头多余的 `AND`。**

例如：

```xml
<where>
    <if test="status != null">
        and status = #{status}
    </if>
</where>
```

最终不会生成：

```sql
where and status = 1
```

而会自动处理成：

```sql
where status = 1
```

因此使用 `<where>` 可以减少手动处理 SQL 拼接问题。

------

#### 3. `<foreach>`：处理 List 集合

当 Mapper 接收到的是一个集合时，例如：

```java
List<Long> ids
```

通常需要使用 `<foreach>`。

在苍穹外卖中，一个典型场景就是：

```text
批量删除
```

例如前端传递：

```text
ids = [1, 2, 3]
```

我们希望最终 SQL 变成：

```sql
delete from dish
where id in (1,2,3)
```

就可以使用：

```xml
<delete id="deleteByIds">
    delete from dish
    where id in
    <foreach collection="ids"
             item="id"
             separator=","
             open="("
             close=")">
        #{id}
    </foreach>
</delete>
```

其中：

```text
collection="ids"
```

表示遍历哪个集合。

```text
item="id"
```

表示当前遍历出来的每一个元素。

```text
separator=","
```

表示元素之间使用逗号分隔。

```text
open="("
close=")"
```

表示整个结果前后加括号。

最终：

```text
[1, 2, 3]
```

会被拼接成：

```sql
(1,2,3)
```

所以可以简单记：

> **只要 SQL 需要遍历一个 List 集合，就很可能会使用 `<foreach>`。**

典型场景包括：

```text
批量删除
批量插入
IN 查询
套餐与菜品关联
订单明细批量保存
```

------

#### 4. 动态 SQL 中为什么不能直接写 `<` 和 `>`？

在 MyBatis XML 文件中，SQL 本身写在 XML 中。

而 `<`、`>` 本身属于 XML 的特殊符号，因此有些情况下不能直接写。

例如：

```sql
create_time < #{endTime}
```

通常可以写成：

```xml
create_time &lt; #{endTime}
```

对应关系：

```text
&lt;   →   <
&gt;   →   >
```

这是因为 MyBatis Mapper 文件本质上首先是一个 XML 文件，所以需要遵守 XML 的语法规则。

------

#### 我对动态 SQL 的理解

以前写 SQL 时，我更习惯认为：

```text
一条 SQL 的查询条件是固定的
```

但实际后端开发中，前端传递的查询条件往往是不确定的，因此需要根据参数动态决定 SQL 应该包含哪些部分。

可以概括为：

```text
前端传入查询参数
        ↓
判断参数是否存在
        ↓
<if> 决定是否添加条件
        ↓
<where> 处理 WHERE 和 AND
        ↓
<foreach> 处理集合参数
        ↓
生成最终 SQL
        ↓
执行数据库查询
```

------

#### 通过这一部分，我主要掌握了

1. 学会了使用 `<if>` 根据参数是否为空动态添加查询条件；
2. 学会了使用 `<where>` 自动处理 `WHERE` 和多余的 `AND`；
3. 学会了使用 `<foreach>` 遍历 `List` 集合；
4. 理解了 `<foreach>` 常用于批量删除、批量插入和 `IN` 查询；
5. 理解了动态 SQL 的核心作用是解决“查询条件不固定”的问题；
6. 知道了 Mapper XML 中 `<`、`>` 等特殊字符需要遵守 XML 转义规则。

最终可以把 MyBatis 动态 SQL 简单理解为：

> **根据实际传入的参数，在运行时动态决定 SQL 应该拼接哪些条件，从而让同一个 Mapper 方法适应不同的查询情况。**

常见标签可以直接记成：

```text
<if>       → 判断参数，有值才拼接

<where>    → 自动处理 WHERE 和 AND

<foreach>  → 遍历集合，常用于 IN、批量删除、批量插入
```

### 6、学会了使用事务保证多步数据库操作的一致性

在苍穹外卖项目中，我学习了使用 Spring 的事务来保证多个数据库操作能够作为一个整体执行。

在实际业务中，一个功能往往不只是执行一条 SQL，而是可能需要连续操作多张表。

例如新增套餐时，需要先向 `setmeal` 表中插入套餐基本信息，然后再向 `setmeal_dish` 表中插入套餐和菜品之间的关联关系。

整体流程大致为：

```text
新增套餐
   ↓
向 setmeal 表插入套餐数据
   ↓
获取新生成的套餐 id
   ↓
给每一条套餐菜品关系设置 setmealId
   ↓
批量插入 setmeal_dish 表
```

如果不使用事务，就可能出现这样的问题：

```text
setmeal 插入成功
        ↓
setmeal_dish 插入失败
        ↓
数据库中出现了一个没有菜品关系的套餐
```

这时虽然第一条 SQL 已经成功执行，但整个“新增套餐”业务实际上是失败的，数据库中的数据就会出现不一致。

因此，需要使用：

```java
@Transactional
```

将这一整段业务操作放到同一个事务中。

例如：

```java
@Transactional
public void saveWithDish(SetmealDTO setmealDTO) {

    Setmeal setmeal = new Setmeal();

    BeanUtils.copyProperties(setmealDTO, setmeal);

    // 插入套餐基本信息
    setmealMapper.insert(setmeal);

    Long setmealId = setmeal.getId();

    List<SetmealDish> setmealDishes = setmealDTO.getSetmealDishes();

    setmealDishes.forEach(setmealDish -> {
        setmealDish.setSetmealId(setmealId);
    });

    // 批量插入套餐菜品关系
    setmealDishMapper.insertBatch(setmealDishes);
}
```

在方法上添加：

```java
@Transactional
```

之后，可以把整个方法中的数据库操作看成一个整体：

```text
全部执行成功
      ↓
提交事务
      ↓
数据库真正保存数据
```

如果中间任何一步出现异常：

```text
某一步执行失败
      ↓
事务回滚
      ↓
之前已经执行的数据库操作也撤销
```

也就是：

> **要么全部成功，要么全部失败。**

------

#### 1. 事务主要解决什么问题？

事务主要解决的是：

> **多个数据库操作之间的数据一致性问题。**

例如：

```text
操作1：新增订单
操作2：新增订单明细
操作3：清空购物车
```

如果前两步成功，但是第三步失败，那么整个下单业务就可能出现异常状态。

使用事务之后：

```text
新增订单
   ↓
新增订单明细
   ↓
清空购物车
   ↓
全部成功
   ↓
提交事务
```

如果其中任何一步出现异常：

```text
新增订单成功
   ↓
新增订单明细失败
   ↓
抛出异常
   ↓
事务回滚
   ↓
新增订单操作也被撤销
```

从而保证业务数据的完整性。

------

#### 2. 苍穹外卖中哪些场景适合使用事务？

在苍穹外卖项目中，只要一个业务涉及：

```text
多张表
+
多次数据库操作
```

就要考虑是否需要事务。

例如：

```text
新增套餐
setmeal + setmeal_dish
修改套餐
更新 setmeal
+
删除原来的 setmeal_dish
+
重新插入新的 setmeal_dish
```

以及订单业务：

```text
新增 orders
+
新增 order_detail
+
清空 shopping_cart
```

这些操作在业务上属于一个整体，因此通常都需要事务进行保护。

------

#### 3. `@Transactional` 的作用

Spring 中可以通过：

```java
@Transactional
```

开启事务。

一般将它加在 Service 层的业务方法上：

```java
@Transactional
public void update(SetmealDTO setmealDTO) {
    ...
}
```

因为 Service 层本身就是负责处理业务逻辑的，而事务通常也是围绕一个完整的业务来控制的。

所以：

```text
Controller
    ↓
Service  ← 事务通常写在这里
    ↓
Mapper
    ↓
Database
```

而不是通常直接写在 Controller 层。

------

#### 4. 事务回滚

事务的一个重要能力就是：

```text
Rollback
```

也就是事务回滚。

假设一共执行三条 SQL：

```text
SQL 1  ✅
SQL 2  ✅
SQL 3  ❌
```

如果没有事务：

```text
SQL 1、SQL 2 已经生效
SQL 3 失败
```

数据库就可能只保存了一部分数据。

而使用事务后：

```text
SQL 1  ✅
SQL 2  ✅
SQL 3  ❌
   ↓
发生异常
   ↓
事务回滚
   ↓
SQL 1 和 SQL 2 也撤销
```

最终数据库恢复到执行这个业务之前的状态。

------

#### 5. 对事务的理解

我现在对事务的理解可以概括为：

> **事务就是把一组数据库操作绑定成一个整体，这组操作要么全部成功，要么全部失败，从而保证数据的一致性。**

可以简单记成：

```text
一个业务
  ↓
多条 SQL
  ↓
@Transactional
  ↓

全部成功 → commit 提交

任何一步失败 → rollback 回滚
```

------

#### 6. 通过这一部分，我主要掌握了

1. 理解了为什么复杂业务不能只考虑单条 SQL 是否成功；
2. 学会了使用 `@Transactional` 开启 Spring 事务；
3. 理解了事务通常应该放在 Service 层业务方法上；
4. 理解了事务的核心作用是保证多个数据库操作的数据一致性；
5. 理解了 `commit` 提交和 `rollback` 回滚的基本概念；
6. 学会了在多表操作、多步骤业务中判断是否需要事务。

最终可以将事务概括为一句话：

> **当一个业务需要执行多次数据库操作，并且这些操作在业务上必须同时成功或同时失败时，就应该使用事务。**

例如苍穹外卖中的：

```text
套餐新增
套餐修改
订单创建
```

都属于非常典型的事务使用场景。

### 7、学会了使用 MyBatis 主键回显获取新增数据的主键 id

在苍穹外卖项目中，我学习了 MyBatis 的**主键回显**功能。

在执行新增操作时，数据库通常会自动生成主键 id，例如：

```sql
id bigint auto_increment
```

假设新增一个套餐：

```java
Setmeal setmeal = new Setmeal();
setmealMapper.insert(setmeal);
```

数据库执行完成后，数据库中的这条记录已经拥有了一个新的主键 id，例如：

```text
id = 15
```

但是如果没有配置主键回显，Java 中原来的 `setmeal` 对象：

```java
setmeal.getId()
```

可能仍然得到：

```text
null
```

这就会影响后续业务。

------

#### 1. 为什么需要主键回显？

例如新增套餐时，需要先插入套餐基本信息：

```text
setmeal
```

然后还要向：

```text
setmeal_dish
```

表中插入套餐和菜品之间的关联关系。

整体业务为：

```text
新增套餐
   ↓
插入 setmeal 表
   ↓
数据库自动生成套餐 id
   ↓
获取这个套餐 id
   ↓
给每一个 SetmealDish 设置 setmealId
   ↓
批量插入 setmeal_dish 表
```

因此，在执行：

```java
setmealMapper.insert(setmeal);
```

之后，我们必须能够获取刚刚新增套餐的 id：

```java
Long setmealId = setmeal.getId();
```

如果没有主键回显：

```java
setmeal.getId()
```

可能为：

```text
null
```

那么后面的套餐菜品关联关系就无法正确保存。

------

#### 2. MyBatis 中如何配置主键回显？

可以在 Mapper XML 中配置：

```xml
<insert id="insert"
        useGeneratedKeys="true"
        keyProperty="id">

    insert into setmeal(...)
    values (...)

</insert>
```

其中：

```text
useGeneratedKeys="true"
```

表示：

> 使用数据库自动生成的主键。

而：

```text
keyProperty="id"
```

表示：

> 将数据库生成的主键值回填到 Java 对象的 `id` 属性中。

因此执行：

```java
setmealMapper.insert(setmeal);
```

之前：

```text
setmeal.id = null
```

数据库插入成功后：

```text
数据库生成 id = 15
```

MyBatis 会自动把这个值回填：

```text
setmeal.id = 15
```

此时：

```java
Long setmealId = setmeal.getId();
```

就能够正常得到：

```text
15
```

------

#### 3. 主键回显的完整流程

可以理解为：

```text
Java 创建对象
   ↓
id = null
   ↓
Mapper 执行 INSERT
   ↓
MySQL 自动生成主键
   ↓
id = 15
   ↓
MyBatis 获取生成的主键
   ↓
回填到原来的 Java 对象
   ↓
setmeal.getId() = 15
```

因此，主键回显并不是重新查询数据库，而是：

> **数据库插入成功后，MyBatis 将数据库生成的主键直接写回原来的 Java 对象。**

------

#### 4. 苍穹外卖中的实际应用

例如套餐新增：

```java
setmealMapper.insert(setmeal);

Long setmealId = setmeal.getId();
```

获取套餐 id 后：

```java
setmealDishes.forEach(setmealDish -> {
    setmealDish.setSetmealId(setmealId);
});
```

然后批量插入套餐菜品关系：

```java
setmealDishMapper.insertBatch(setmealDishes);
```

整个过程：

```text
插入套餐
   ↓
主键回显
   ↓
获得 setmealId
   ↓
设置套餐菜品关联表中的 setmealId
   ↓
批量插入关联数据
```

因此主键回显对于这种：

```text
先插入主表
   ↓
获取主表主键
   ↓
再插入从表
```

的业务非常重要。

------

#### 5. 对主键回显的理解

我现在可以把主键回显简单理解为：

> **新增数据时，数据库自动生成主键，MyBatis 再把这个主键值回填到原来的 Java 对象中，使后续业务可以直接通过 `getId()` 获取新增数据的主键。**

需要特别注意：

> **主键回显解决的不是“对象为 null”的问题，而是“对象存在，但是它的 id 属性为 null”的问题。**

例如：

```java
Setmeal setmeal = new Setmeal();
```

这个对象本身：

```text
setmeal ≠ null
```

但是：

```java
setmeal.getId() == null
```

主键回显解决的是第二种情况。

------

#### 6. 一句话总结

可以直接记：

> **当新增主表数据后，后续业务还需要使用数据库自动生成的主键 id 时，需要配置 MyBatis 主键回显，将生成的 id 回填到 Java 对象中。**

常见配置：

```xml
useGeneratedKeys="true"
keyProperty="id"
```

典型业务：

```text
主表新增
   ↓
获取自动生成的主键
   ↓
从表使用这个主键建立关联
```
